# Memory 无限 v2.18 模块整改台账

## 1. 口径

本台账补齐 V0 时承诺但此前没有形成正式文件的交付物：每个模块当前在哪里、发现了什么、已经怎样修、下一步怎样修、预计影响多少行、用什么证据验收。

- V0 基线：`72998fd4e051816f57ac2c56d94579e0db45f8b1`
- V1 架构门禁：`c4ae78dabae8c0f2618288d6e6a5957af07cf6a7`
- V2 当前状态：`6c514ccbdd075a5f45cf1d956471177edf7555ee`
- 生产范围：`scripts/**/*.py|ps1|sh`、`native-collector/src/**/*.rs`、`packaging/**`
- 计数方法：读取 Git 对象和当前文件，按物理行计数；空行也计入。

状态定义：

- **已完成/实测**：代码已经落地，行数和验证结果可从提交与收据复算。
- **待实施/估算**：策略已确定，但代码尚未修改；行数只能给范围或明确不估。
- **延期**：当前明确不动，避免触碰尚未稳定的摘要合同。

## 6. 实施顺序

1. V3a：只做批处理结果类型化，运行 Rust 定向测试、JSON 黄金夹具和架构门禁。
2. V3b：只做事件循环共同状态转换，分别彩排 Windows 与 macOS 路径。
3. 独立复核 V3 的 diff、复杂度和行为证据；通过后再进入 V4。
4. V4 先提交性能夹具，不先提交优化；随后一次只改消息缓存、SourceSnapshot 或 BuildContext 中的一项。
5. 每个小补丁只跑影响范围彩排；最终候选版本才跑一次全量彩排。不得为发现一个小问题连续发布多个补丁版。
6. 摘要与确定性索引继续冻结，等新摘要模块满足重启条件后作为独立阶段处理。

## 7. 结论

此前真正完成的是 V1 和 V2，不是整套 V0-V4。V1/V2 已经有提交、验证收据和实测行数；V3/V4 仍是待实施工作。本台账以后作为该轮结构梳理的唯一进度入口，不能再用聊天中的零散结论代替。
